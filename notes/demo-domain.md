# 作品集演示场景推荐（Phase 0）

## 结论：选 (b) 多源网络研究智能体（带引用）

给定一个研究问题，智能体并行检索多个来源，综合成一份带逐条引用的简报。

## 对比

| 维度 | (a) 开源项目 triage / 研究简报 | (b) 多源网络研究（带引用） |
|---|---|---|
| 练到 CodeAgent 的核心能力 | 中：读代码、读 issue、归纳 | 高：检索、综合、引用、结构化输出 |
| 与 Phase 5（Anthropic orchestrator-worker 多智能体）的契合 | 低：triage 主要是单线归纳 | 高：主智能体拆问题 → 3–5 个并行研究子智能体 → 综合 + 引用智能体，正好是那篇博客的模式 |
| 评测（Phase 7）能不能客观打分 | 难：triage 质量主观，没标准答案 | 易：自写 GAIA 风格题库，每题有可核查的答案和来源 |
| 作品集可读性 | 中：triage 报告要懂行才评得出好坏 | 高：任何人都能读简报、点引用验证 |
| 成本/外部依赖 | GitHub API（未认证 60 请求/小时，需 token；或 clone 仓库读本地） | DDGS 搜索免费；token 消耗在综合环节，可控 |
| 范围可控性 | 易发散：选哪些仓库、挖多深 | 好收敛：问题进、简报出 |
| 与已有工作的重叠 | 与 mini-swe-agent 的“仓库+代码”方向撞 | 与现有 mini-agent（计算/读文件/搜索）无重叠，是新能力 |

## 选 (b) 的理由

1. **直接对上 CodeAgent 的长处**：多步检索 + 代码内组合 + 引用输出，是
   smolagents 最出彩的演示形态，也是 Phase 4 要验证“代码步数比 JSON 少”的地方。
2. **Phase 5 有现成设计稿**：Anthropic 多智能体研究系统的 orchestrator-worker
   模式（主智能体规划、并行子智能体、引用智能体）可以直接落在 (b) 上，
   不用再为多智能体另找场景。
3. **评测真实**：Phase 7 可以自写 15–30 道有标准答案的研究题（人物、数字、
   时间、来源），成功率、步数、token 都能量化；(a) 的 triage 只能靠人工打分。
4. **演示效果直观**：一份带引用的简报，招聘方 2 分钟就能看懂好坏；(a) 的
   triage 报告需要读者自己懂那个仓库。
5. **避开用户日活领域**：研究题选通用主题（科技、科学、历史），不碰风控审核。

## (a) 的去处

不丢，作为 **Phase 8 的扩展演示**：复用 (b) 的检索/综合能力 + 文件/代码
工具，给定一个 GitHub 仓库出 triage 简报（issue 分类、陈旧问题、建议优先项）。
两个场景共用同一套 agent，作品集里是“一个智能体，两种演示”，比单场景强。

## 待定（Phase 0 不做决定，留给 Phase 1–2）

- 研究题库的具体选题（Phase 7 再定，15–30 道）。
- 引用格式：行内 `[来源]` 还是文末列表（看 Phase 4 的解析成本）。
- 子智能体并行数上限：免费层限速，Phase 5 实测后再定（先按 3–5 个估）。
